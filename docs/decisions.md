# fee-service — Decisions

The decision log and the open questions. Design: [`design.md`](design.md). Task checklist: [`../tasks.md`](../tasks.md).
When a decision changes, update this file in the same change. A resolved open question becomes a new `D` row.

## Decisions

| # | Topic | Decision |
|---|-------|----------|
| D1 | Build | **Maven** 3.9+, the system `mvn` (no wrapper: the dev image in `dev-setup/` pins the version), `kotlin-maven-plugin` (with the `spring` compiler plugin and `kapt`) |
| D2 | Web | **Spring Boot** (`spring-boot-starter-web`). The `@RestController` serves `POST /transaction/fee` |
| D3 | Money | **`BigDecimal`** everywhere, never `Double`; `HALF_EVEN` rounding at the asset's decimals |
| D4 | Restate SDK | **Restate Java SDK 2.9.3** (`dev.restate:sdk-java-http`), used from Kotlin. `sdk-api-gen` runs through kapt; Jackson 2 is shared with Spring (the library and its version, not the `ObjectMapper` instance: Restate's serde has its own mapper, D35) |
| D5 | Restate server | Runs in Docker **outside** this project. The app needs only the ingress and admin URLs, both configurable |
| D6 | Storage | **Restate only.** No database. Workflow state holds each run's outcome; Virtual Object state holds the permanent fee record |
| D7 | **Logic placement** | **Everything runs inside `FeeWorkflow`** as journaled steps: validate → map → claim → calculate → charge → record. `FeeService` only checks the routing key, builds the workflow key, submits or attaches, and maps the outcome to HTTP |
| D8 | **Workflow key** | `{transaction_id}:{payloadHash}`. Re-sending the same payload → same workflow → Restate's "previously accepted" → attach and get the same result. A **changed payload** (e.g. the state went from `PENDING` to `SETTLED - PENDING FEE`) → a new workflow. So a rejected request **does not use up** the `transaction_id`. Duplicate charges for one `transaction_id` are prevented by the claim on `TransactionFeeRecord/{transaction_id}` |
| D9 | Workflow result | The workflow **returns** a sealed `FeeOutcome` (`Charged`, `Rejected`, `Conflict`, `Failed`) instead of throwing for business errors, so no parsing of error messages. `FeeService` maps it: 200 / 400 or 422 / 409 / 422 |
| D10 | Parsing | Enum fields arrive as `String`. Each enum has `UNKNOWN` and a `fromValue(raw)` that never throws. `TransactionMapper` runs only after validation passes and never throws |
| D11 | Validation | **`List<TransactionValidator>` beans ordered by `@Order`**, **fail-fast**, executed **inside the workflow** in `ctx.run("validate")`, so the result (including the `Clock`-based "not in the future" check) is journaled and deterministic on replay. `@Order` is a Spring annotation, not a Restate one: Spring injects the list already sorted when it builds the `FeeWorkflow` bean, and Restate never sees the validators. The order still matters: the first failure decides the response, and later validators rely on earlier ones (fields present, asset known). `ValidationError.kind`: `INVALID` → 400, `UNSUPPORTED` → 422. All 400 checks (malformed request) run before all 422 checks (well-formed but not supported). Too many decimals for the asset is a 422, because the allowed decimals belong to the asset |
| D12 | Accepted state | **Only `SETTLED - PENDING FEE`.** Anything else → 422 *"Unsupported state 'PENDING'. Supported: 'SETTLED - PENDING FEE'"* |
| D13 | Assets | **Only `USD` and `EUR`** (both `FIAT`, 2 decimals) |
| D14 | Fee rules | **`List<FeeRule>` beans**, one per `TransactionType`, indexed in `FeeCalculator`; startup fails on a missing or duplicate rule |
| D15 | **Registration** | `RestateRegistrar` runs on `ApplicationReadyEvent`: it asks the admin API whether our endpoint (`restate.advertised-url`) is registered with the current services. **If it is missing, it registers; if the services changed, it re-registers with `force`**; if it is up to date, it does nothing. Retries with backoff while the admin API is unreachable. **If it still fails after `maxAttempts`: log a WARN and keep the app running** (no startup failure), and keep retrying in the background at the max backoff until it succeeds. The current `RegistrationStatus` (`PENDING` / `REGISTERED` / `FAILING`) is kept in a bean. A code comment marks it as the hook for a future **Actuator readiness indicator** (Kubernetes readiness probe). Switch: `restate.registration.enabled` |
| D16 | **Endpoint lifecycle** | The Restate endpoint server is a `SmartLifecycle` bean (`RestateEndpointLifecycle`). It starts after the context and stops gracefully, and **tests can stop and start it** to simulate a crash or restart |
| D17 | **Fault injection** | `FeeWorkflow` calls a `StepHook` (`before(step)` / `after(step)`) around each step. Production uses `NoOpStepHook`; tests swap in `FaultInjectingStepHook` to "crash" at any step boundary |
| D18 | Tests | **JUnit 5 + Mockito + Testcontainers** (Restate container) + **Cucumber**. Heavy focus on workflow, recovery and restart scenarios. Integration tests use **only random ports** (Restate container ports mapped by Testcontainers, the API on `RANDOM_PORT`, a free endpoint port picked per run) and override every `restate.*` setting, so a Restate or app already running on the machine can't interfere |
| D19 | Errors | Spring's built-in `ProblemDetail` (RFC 7807) |
| D20 | Time | An injected `Clock` bean, read only inside `ctx.run`, so the value is journaled |
| D21 | **Contract DTOs** | `FeeRequest`, `FeeResponse` and `FeeStatusResponse` live in `contract`, not `api`, so `validation`, `restate` and `application` never import `api`. `FeeRequest` is journaled as the workflow input and `FeeResponse` is stored permanently in `TransactionFeeRecord`, so **their JSON shape is stored state**: renaming or removing a field is a breaking change for in-flight workflows and existing records. Adding a nullable field is safe |
| D22 | **Runtime configuration** | Every tunable value comes from Spring Boot's externalized configuration, so changing it needs **a restart, not a rebuild**. Defaults live only in the packaged `application.yml`; Kotlin code doesn't repeat them. Overrides: environment variables, a `config/application.yml` in the working directory (or `--spring.config.additional-location`), command-line arguments; on Kubernetes a ConfigMap. **Configurable:** `server.port`, `restate.*`, the fee numbers (D23). **Stays in code:** which formula a type uses (D14), the supported states and assets (D12, D13), the description wording. The `restate.*` keys use explicit placeholders (`${RESTATE_INGRESS_URL:…}`) because Spring's automatic mapping drops dashes (`RESTATE_INGRESSURL`). No hot reload and no Spring Cloud Config: a restart is enough, and it would be a new dependency. Changing `restate.advertised-url` registers a new deployment, while in-flight invocations stay on the old URL (open question 4) |
| D23 | **Fee configuration** | Each `FeeRule` bean is built from its own `@ConfigurationProperties` class (`fee.<type>`: `rate`, `min`, `fixed` as the formula needs), found by `@ConfigurationPropertiesScan`. A new type is still "add classes"; no central class grows a field per type. Values are checked in `init` with `require` (rate in [0, 1), amounts ≥ 0), so a missing or invalid value fails startup without the validation starter. Money values are quoted in YAML. Descriptions are **built from the configured numbers and the transaction's asset** (`Fee rate of 0.5% (min 1.00 EUR)`), so they can't go stale or name the wrong currency. The numbers are read inside CALCULATE's `ctx.run`, so a calculated fee is journaled, and completed records keep the fee they were charged with. Bank Transfer has a minimum and **no maximum for now** |
| D24 | **Demo wallet delay** | `FakeWalletGateway` waits `wallet.fake.delay` (default `0s`) before it records a charge, so the demo can kill the app in the middle of CHARGE and show Restate resuming with one charge. The wait comes before the charge, so a kill during it leaves nothing charged. Tests don't use it: `TestWalletGateway` blocks on a latch instead |
| D25 | **Build versions** | JDK 25. Spring Boot **3.5.x**, not 4.x: Boot 4 moves Spring MVC to Jackson 3 (`tools.jackson`) and renames `spring-boot-starter-web` to `spring-boot-starter-webmvc`, both outside the approved stack, while Restate SDK 2.9.3 is built on Jackson 2, which D4 shares with Spring. `pom.xml` raises Boot's managed versions to what the SDK is built against: Kotlin 2.3.21 (Boot 3.5 pins 1.9, which can neither read the SDK's Kotlin 2.3 metadata nor target JDK 25), Jackson 2.22, OpenTelemetry 1.58. Cucumber 7.34 runs on JUnit 5.14 (Cucumber 8 needs JUnit 6 and Spring 7). `log4j-core` is excluded from the SDK, so the SDK's log4j-api logging goes through Logback. Tests load Mockito as a `-javaagent` instead of letting it self-attach. Moving to Boot 4 is future work, and it needs Jackson 3 approved (autonomous decision, review) |
| D26 | **Clock zone** | The `Clock` bean is `Clock.systemUTC()`, not the host's zone. `created_at` carries no zone, so the "not in the future" check (`CreatedAtValidator`) reads it as UTC and behaves the same on every host. A client that sends local time from a zone east of UTC looks up to that offset "in the future" and gets a 400 (autonomous decision, review) |
| D27 | **Restate outage in tests** | The ITs simulate a Restate outage by **freezing** the Restate container with `SIGSTOP` and thawing it with `SIGCONT` (`killContainerCmd(id).withSignal(…)` on Testcontainers' Docker client), not with `pause`. For the app the effect is the same: connections are accepted, nothing answers until the thaw. Pause needs a cgroup per container, which the dev container's nested podman can't create without extra privilege (the dev container's cgroup belongs to its uid 0, the nested podman runs as the user); signals need none and work on Docker and in CI too. The signal reaches the container's main process, `restate-server`; `dev-setup/check-nested-podman.sh` checks that a frozen Restate stops answering |
| D28 | **Restate server version** | Pin **Restate 1.8.1**: the dev Restate (`latest`) reports 1.8.1, and spike 0.2 ran everything below against it. SDK 2.9.3 registers as `BidiStream` over HTTP/2 with service protocol versions 5–7; the server accepts admin API versions 2–5. Tests (`RestateTestEnvironment`, 7.1): `docker.io/restatedev/restate:1.8.1`, fully qualified so the nested podman needs no short-name resolution. The spike started it with Testcontainers, registered an endpoint through `host.testcontainers.internal` and ran a workflow. `dev-setup/compose.yaml` (the user pins it): `image: docker.restate.dev/restatedev/restate:1.8.1`, the same tag as on Docker Hub (autonomous decision, review) |
| D29 | **Handler API in SDK 2.9** | Resolves open question 6. SDK 2.9 deprecates for removal the ctx-based codegen API (`Context`, `WorkflowContext`, the kapt-generated `*Client` / `*Handlers` / `*ServiceDefinitionFactory`) in favour of a reflection-based API without `ctx`. **We keep the codegen API on the pinned 2.9.3**: AGENTS.md fixes it, spike 0.2 verified it, and 2.9.3 doesn't remove it. Files that use it start with `@file:Suppress("DEPRECATION")`. Migrating needs a stack change approved by the user, before any SDK upgrade that removes the API (autonomous decision, review) |
| D30 | **Submit, attach, retention** | `FeeWorkflowClient.fromClient(client, key).submit(input)` never throws on a duplicate: the first returns `sendStatus() == ACCEPTED`, a later one `PREVIOUSLY_ACCEPTED` with the same invocation id, and **its input is ignored** (hence the payload hash in the key, D8). `FeeService` always submits, then attaches (`attachAsync()`, `get(attachTimeout)`, `TimeoutException` → 202). Ingress unreachable → `IngressException` with `statusCode == -1`, wrapped in a `CompletionException` → 503. `getOutput()` for an unknown key → `IngressException` 404. `@Shared status()` answers while `run` is in flight and for a key that never ran; the VO's `@Shared get()` returns `null` without state. Retention on 1.8.1: workflow, idempotency and journal all **1 day**, kept; after it a resubmission goes CLAIM → `AlreadyCompleted` (7.5) |
| D31 | **Admin API: registration and "services changed"** | On 1.8.1: `GET /deployments` → `{"deployments":[{"id","uri","services":[{"name","revision"}]}]}`; `uri` is stored **with a trailing slash**, so the registrar compares a normalized `restate.advertised-url`. `POST /deployments {"uri"}`: new URI → 201; known URI → 200 with the existing deployment and **no discovery** (`force` defaults to false), so changed services are silently ignored. `force:true` → 200, updated in place (same id). `{"uri","force":true,"dry_run":true}` returns the discovered services without applying them; `GET /deployments/{id}` returns the registered ones. **Detection:** no deployment with our URI → `POST {uri}`; otherwise dry run and compare by service name and type, and handler name, type, `input_description` and `output_description` (a full JSON comparison differs even when nothing changed); different → `POST {uri, force:true}`, equal → nothing. `DELETE /deployments/{id}` needs `?force=true` (else 501), and removing a service's last deployment removes the service. The same services under another URI become a new deployment that new invocations go to (open question 4) |
| D32 | **Starting and stopping the endpoint** | `RestateHttpServer.listen(endpoint, port)` can't be stopped, so `RestateEndpointLifecycle` owns a Vert.x instance: `Vertx.vertx()` → `RestateHttpServer.fromEndpoint(vertx, endpoint)` → `HttpServer.listen(port)` / `actualPort()`; stop with `HttpServer.close()`, then `Vertx.close()` (frees the port, no `vert.x-*` threads left, restart on the same port works). `io.vertx:vertx-core` is only a runtime dependency of the SDK, so these calls and `Future.toCompletionStage()` go **by reflection**, guarded by its unit test (5.2, open question 7). `close()` is **not graceful**: open connections drop, Restate retries, and a `ctx.run` closure that was running runs again (the old thread may still finish), so the wallet must stay idempotent by key (autonomous decision, review) |
| D33 | **Retries and fault injection** | A plain exception thrown between steps (outside `ctx.run`) makes Restate rerun the handler from the top, **replaying** journaled steps instead of executing them. So `StepHook` (D17) injects a crash by throwing, and recovery tests count `ctx.run` closure executions, not hook calls. A plain exception inside `ctx.run` does the same (3 failures take ≈ 4.4 s). A `TerminalException` inside the closure is journaled and rethrown from `ctx.run`, never retried; a resubmission returns the same `Failed`. **Defaults on 1.8.1:** retries 500 ms, ×2, at most 1 min apart, 70 attempts, then **`Pause`** (the record stays `IN_PROGRESS`, open question 5); `inactivity_timeout` 1 min, `abort_timeout` 10 min. ITs use bounded polling sized for these, never `Thread.sleep` |
| D34 | **Binding Spring-built beans** | `Endpoint.builder().bind(bean)` finds the kapt-generated `ServiceDefinitionFactory` through `ServiceLoader` (`supports(obj)` is an `instanceof` check, so a CGLIB subclass matches too) and binds **that instance**. So `FeeWorkflow` and `TransactionFeeRecord`, built by Spring with constructor injection, bind as they are. `RestateEndpointLifecycle` builds the `Endpoint` from the two beans; `RestateRegistrar` needs nothing from it (D31 compares on the server side) |
| D35 | **Serde of durable types** | Generated code serializes with `new JacksonSerdeFactory()`, Restate's own `ObjectMapper().findAndRegisterModules()` (Kotlin module, JSR-310), **not Spring's mapper**. In it, `@JsonProperty` snake_case works as in Spring; `BigDecimal` is a plain number and keeps its scale (`1.50`); a missing nullable property reads as `null`; `ctx.run` returning `null` journals and replays `null`. `FAIL_ON_UNKNOWN_PROPERTIES` is **on**, so (D21) renaming or removing a field is breaking, adding a nullable one is safe, and rolling back past a release that added a field is breaking. Sealed types: `@JsonTypeInfo(use = NAME, property = "@type")` **plus explicit `@JsonSubTypes` names** (`"CHARGED"`, `"NEW"`, …), because the default id is the class name and only `@JsonSubTypes` shows subtypes in Restate's schema. `data object` subtypes deserialize to new instances: compare with `==`, `is` or `when`, never `===`. Durable-type tests (4.3) use `JacksonSerdeFactory()` (autonomous decision, review) |
| D36 | **Restate setting defaults** | Packaged defaults for the values the plan left open: `restate.attach-timeout` **10s** (enough for a normal run, so 202 is only for slow ones), `restate.registration.max-attempts` **10**, `restate.registration.backoff` **2s**, `enabled` **true**. Variables: `RESTATE_ATTACH_TIMEOUT`, `RESTATE_REGISTRATION_ENABLED`, `RESTATE_REGISTRATION_MAX_ATTEMPTS`, `RESTATE_REGISTRATION_BACKOFF`. `server.port` has no placeholder: Spring maps `SERVER_PORT` itself (autonomous decision, review) |
| D37 | **Enum parsing** | `fromValue(raw)` matches `value` exactly: case-sensitive, no trimming (`"usd"`, `" USD"` → `UNKNOWN`), because the contract's values are fixed strings and the payload hash (D8) is taken from the raw request. `UNKNOWN` is never matched by its own name. `TransactionState` and `AssetType` list only the supported values (`SETTLED_PENDING_FEE`, `FIAT`); `Asset.UNKNOWN` has 0 decimals, never used because validation rejects it first (autonomous decision, review) |
| D38 | **Contract JSON** | Every `BigDecimal` field in `contract` carries `@JsonSerialize(using = PlainBigDecimalSerializer::class)`: a per-field annotation is the only setting both Spring's and Restate's mapper (D35) honour. It writes a plain number keeping the scale (`1E+3` → `1000`, `1.50` stays); beyond scale ±9999 it falls back to scientific, so a hostile `1e999999999` can't blow memory before validation. `FeeResponse` fields are non-null; `asset` and `type` are the contract strings, not enums. `FeeStatusResponse.status` is its own enum `IN_PROGRESS` / `COMPLETED` / `FAILED`, built with `inProgress` / `completed(response)` / `failed`, nulls omitted (autonomous decision, review) |
| D39 | **Mapping** | `Transaction` holds parsed values (enums, `createdAt` as `LocalDateTime`, the amount with its scale as sent). `TransactionMapper.toTransaction(request)` returns `Transaction?`: `null` when `transaction_id`, `amount` or a parseable `created_at` is missing, which validation rules out, so it never throws and never invents a value; `FeeWorkflow` (4.5) treats `null` as a bug (a plain exception), not a business result. `created_at` is `uuuu-MM-dd HH:mm:ss` plus 0–9 optional fraction digits, `STRICT` (no `T`, no zone, no impossible dates), parsed only by `CreatedAtFormat.parseOrNull`, which `CreatedAtValidator` (3.2) reuses (autonomous decision, review) |
| D40 | **Fee building blocks** | `PercentageFee`, `PercentageWithMinimumFee`, `PercentagePlusFixedFee` and `FlatFee` implement `FeeRule` and take `(type, numbers…, description: (Asset) -> String)`, so a rule bean (2.2) is `FeeRule by PercentageFee(…)` and supplies only its numbers and wording. The unrounded result is rounded once (`max(amount × rate, min)`, `amount × rate + fixed`), so `FeeQuote.fee` has the asset's scale (`1.50`, not `1.5`); `rate` is the configured one, also when the minimum applies, and `0` for `FlatFee`. The blocks repeat D23's `require` checks (rate in [0, 1), amounts ≥ 0). `FeeQuote` is what CALCULATE journals (autonomous decision, review) |
| D41 | **Fee properties and wording** | Each `*FeeProperties` is a constructor-bound class with **nullable** constructor parameters and checked non-null `val`s, so a missing value fails with the key's name (`fee.bank-transfer.min is missing…`) rather than a Kotlin null error; a key that isn't a number fails in Spring's conversion (`BindException` naming the key). Descriptions write rates as percentages without trailing zeros (`0.0015` → `0.15%`, `0.01` → `1%`) and amounts at the asset's decimals, `HALF_EVEN` (`1` → `1.00 EUR`) (autonomous decision, review) |
| D42 | **Fee calculator** | `FeeCalculator` indexes `List<FeeRule>` by type in its constructor and fails startup (`IllegalStateException` naming the types and rule classes) on a duplicate rule, a missing rule for any type except `UNKNOWN`, or a rule for `UNKNOWN`. `calculate` for a type without a rule throws `IllegalArgumentException`: validation rules it out, so the workflow treats it as a bug, like D39's `null` (autonomous decision, review) |
| D43 | **Validation types** | `ValidationError(field, value, message, kind)`: `value` is the rejected value as a string, `null` when the field is missing; `kind` is the nested enum `ValidationError.Kind` (`INVALID` → 400, `UNSUPPORTED` → 422), journaled by name. `RequestValidator` sorts its list with `AnnotationAwareOrderComparator` itself, so a validator without `@Order` runs last (autonomous decision, review) |
| D44 | **Structural checks** | All 7 fields are required; a blank text field counts as missing, and the first missing one in contract order is reported (`value` = the blank string, `null` when absent). `transaction_id`: 1–64 ASCII letters, digits, `_`, `-` (it goes into the workflow key, the VO key and the `GET` path), and a missing one is rejected there too, because `FeeService` runs it alone. `amount` > 0 (decimals are D11's 422). `created_at` not after now in UTC; equal passes. Messages echo the value, cut to 64 chars (`ValueDisplay`) (autonomous decision, review) |
| D45 | **Business checks** | Each 422 message is `Unsupported <field> '<value>'. Supported: …`, listing the enum values except `UNKNOWN`; the type list comes from `FeeCalculator.supports`. Decimals ignore trailing zeros (`10.100` USD passes, `10.001` fails: *"Amount 10.001 has 3 decimals. USD allows 2"*), matching the payload hash's normalized amount. `asset_type` is checked against the supported list only, not against the asset's own type, because every supported asset is `FIAT` (autonomous decision, review) |
| D46 | **Wallet contract** | `WalletGateway.charge(idempotencyKey, amount, asset: Asset): ChargeReceipt(charge_id, idempotency_key, amount, asset)`. A repeated key returns the **first receipt unchanged, even for another amount** (no error, which Restate would retry forever). `FakeWalletGateway.chargeCount(key)` is 0 or 1. Its delay is `FakeWalletProperties` (`wallet.fake.delay`, `${WALLET_FAKE_DELAY:0s}`, negative fails startup); it is skipped for a key already charged, and the wait is a constructor `Pause` with a real-sleep default, so unit tests need no sleeping (autonomous decision, review) |
| D47 | **Claim rules and fee record** | `ClaimDecider.decide(record, hash)`: no record or `FAILED` (any hash) → `New`; `IN_PROGRESS` (any hash) → `InProgress`; `COMPLETED` → `AlreadyCompleted(response)` for the same hash, else `Conflict`. It only decides: on `New` the VO (4.4) stores `FeeRecord.inProgress(hash)`, and `complete(response)` / `fail(reason)` return the next record, keeping the hash. `FeeRecord(status, payload_hash, response, failure_reason)` requires `response` exactly when `COMPLETED` and `failure_reason` exactly when `FAILED`, also on deserialization. `ClaimResult` type ids: `NEW`, `ALREADY_COMPLETED`, `IN_PROGRESS`, `CONFLICT` (autonomous decision, review) |
| D48 | **Workflow types** | `FeeWorkflowInput(request, payload_hash)`. `FeeOutcome` type ids: `CHARGED` (`response`), `REJECTED` (`error`), `CONFLICT` (`transaction_id`), `FAILED` (`reason`). `WorkflowStep` is stored by name. `StepHook.before/after(step, workflowKey: String)` takes the key as a string, because `restate` must not import `application`'s `WorkflowKey`. `NoOpStepHook` is a plain `@Component`, so a test hook has to replace that bean rather than sit next to it (autonomous decision, review) |
| D49 | **Fee record object** | `TransactionFeeRecord` keeps one `FeeRecord` under the state key `"record"`. Handlers: `claim(hash): ClaimResult` (stores `FeeRecord.inProgress(hash)` only on `New`), `complete(response)` and `fail(reason)` returning nothing, `@Shared get(): FeeRecord?`. `complete` / `fail` on a record that isn't `IN_PROGRESS` (or none) is a bug: a plain `IllegalStateException`, retried until Restate pauses it, like D39 and D42. Handler KDoc is sent to Restate as documentation, so internal notes there are `//` comments (autonomous decision, review) |
| D50 | **Workflow steps** | `FeeWorkflow.run` writes the step to state key `"step"` before the step's `StepHook.before`, and `DONE` on every return; `@Shared status(): WorkflowStep?` is `null` for a workflow that never started. `ctx.run` names and result types: `"validate"` (`ValidationError?`), `"calculate"` (`FeeQuote`), `"charge"` (`ChargeReceipt`). Wallet idempotency key `fee-{transaction_id}`. CLAIM: `AlreadyCompleted` → `Charged(stored response)`, `InProgress` and `Conflict` → `FeeOutcome.Conflict`. The response's `asset`/`type` are the enums' contract values, `amount` as sent (autonomous decision, review) |
| D51 | **Charge declined** | Inside the `"charge"` `ctx.run` closure a `ChargeDeclinedException` is rethrown as `TerminalException(422, reason)`; `run` catches only code 422 from that `ctx.run`, calls `fail(reason)` as the RECORD step and returns `FeeOutcome.Failed(reason)` (the wallet's reason, not the exception message). Other terminal codes (a cancellation, 409) and plain exceptions propagate, so cancellation handling stays open question 5. The code is journaled: changing it breaks declined in-flight workflows (autonomous decision, review) |
| D52 | **Restate config** | `RestateProperties` follows D41: nullable constructor parameters, checked non-null `val`s; a missing key, a URL that isn't absolute `http(s)`, a port outside 0–65535 (0 = OS picks, tests only), a non-positive `attach-timeout` or `backoff`, or `max-attempts` < 1 fails startup naming the key. `RestateConfig` builds one ingress `Client.connect(ingressUrl, JacksonSerdeFactory())` (opens no connection) and two `fun interface` factories, `FeeWorkflowClients.forKey(workflowKey: String)` and `TransactionFeeRecordClients.forKey(transactionId)`, returning the generated `IngressClient`; the key is a `String` because `restate` must not import `WorkflowKey` (autonomous decision, review) |
| D53 | **Endpoint lifecycle details** | `RestateEndpointLifecycle` runs in the default `SmartLifecycle` phase, so it starts after and stops before the other lifecycle beans, including the web server. `port()` returns the bound port while running (the OS's pick when `endpoint-port` is 0), else `null`. A port that can't be bound **fails startup** with `IllegalStateException` naming the port and `restate.endpoint-port`, unlike registration (D15), because the app can't serve Restate without it. `start` and `stop` are idempotent; `stop` logs a close failure instead of throwing (autonomous decision, review) |
| D54 | **Admin client** | `RestateAdminClient(RestClient.Builder, RestateProperties)` uses Boot's builder (base URL `admin-url`): `listDeployments()`, `deployment(id)`, `register(uri, force = false, dryRun = false)`, which always sends `{"uri","force","dry_run"}`. The response types keep only what D31 compares, so `ServiceDescription`s are `==` when nothing changed (apart from handler order); `uri` is `null` for a non-HTTP deployment. Every failure (unreachable, timeout, error status, unreadable or empty body) is a `RestateAdminException` naming the call. Timeouts are Boot's `spring.http.client.connect-timeout` **5s** / `read-timeout` **30s** (no placeholder, like `server.port`), so a frozen Restate can't stall the registrar (autonomous decision, review) |
| D55 | **Registrar retries** | Refines D15. The first attempt runs on the `ApplicationReadyEvent` thread, so a reachable Restate knows the endpoint before `run()` returns. Each retry runs on Boot's own `TaskScheduler` (`@EnableScheduling` on `RestateConfig` makes Boot create it), `backoff` after the previous failure. The interval is fixed, so the "max backoff" is `backoff`. Any exception counts as a failed attempt. Status: `PENDING` + last error before `max-attempts`, one WARN and `FAILING` at it, `REGISTERED` (error cleared) on success. Disabled → status stays `PENDING`, so the readiness indicator has to treat a disabled registration as ready. Context close cancels a pending retry (autonomous decision, review) |

## Open questions

1. **Same id with a different payload after a charge**: 409 (proposed), or return the original result?
2. **Networking**: the app runs on the host, Restate in Docker reaches it at `host.docker.internal:9080`, and the API is on 8081?
3. **Restate test kit**: Restate publishes `dev.restate:sdk-testing` (a JUnit 5 extension built on Testcontainers). It isn't needed because we test
   registration through our own harness. Keep it out (proposed) or allow it?
4. **Re-registering with `force`** overwrites the deployment in place. Restate warns that this can leave in-flight invocations
   unrecoverable if the handlers changed. That is fine for the challenge (one local instance). On Kubernetes, register each version as a new
   deployment (its own URL) and let the old one drain. That is future work. A changed `restate.advertised-url` (D22) is a related
   case: it registers a new deployment, and invocations in flight on the old URL need that URL reachable until they finish.
5. **Cancelled or killed workflows** leave `TransactionFeeRecord` in `IN_PROGRESS`, so that `transaction_id` gets 409 forever.
   Proposed: catch cancellation (a `TerminalException`) in `run` → `fail(reason)` (safe, because the wallet is idempotent by key). Document
   `kill` as an operator action that needs a manual reset. Spike 0.2 found a third way into this state: after 70 failed attempts (about an
   hour at the default policy, D33), Restate 1.8.1 **pauses** the invocation instead of failing it, so the record stays `IN_PROGRESS` until
   an operator resumes it (it then continues) or kills it (manual reset).
6. *Resolved by D29* (the deprecated handler API in SDK 2.9: keep the codegen API on the pinned 2.9.3).
7. **Vert.x at compile scope**: `RestateEndpointLifecycle` reaches Vert.x through reflection (D32), because `io.vertx:vertx-core` is only a
   runtime dependency of the SDK and declaring it is outside the approved stack. Approving `io.vertx:vertx-core` (the SDK's own version,
   4.5.30 in 2.9.3, already on the runtime classpath) at compile scope would replace the reflection with typed calls. The reflection is
   proposed for now. Approve the dependency or keep the reflection?
